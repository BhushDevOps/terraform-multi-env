Apply dev/env1 — step by step

Repo: terraform-multi-env. Every command, why it is needed, and what you should see. Values are the real ones from live/dev/: account 708485767572, state bucket demo-app-tfstate-bk-dev-708485767572.

0. Credentials→ 1. Bootstrap (once per account)→ 2. 02-eks (once per account)→ 3. env1 (per env)→ 4. Join env1 to cluster
Why this order: each box has its own state file and reads outputs from the box before it. env1 reads 02-eks (when eks_enabled = true), 02-eks needs the state bucket from bootstrap. Nothing reads env1, so env1 is always safe to apply last and to destroy first.

Step 3 — Environment live/dev/env1 once per env

Why it looks odd: env1/ has no .tf files, only backend.hcl and terraform.tfvars. The code is in live/dev/stack/ and is shared by env1, env2, env3. You run the stack folder and point it at env1. Same code, different state key, different values. That is how three environments share one account without colliding.
# 1. Give env1 its own .terraform directory
$env:TF_DATA_DIR = "..\env1\.terraform"

# 2. Init the shared stack against env1's state key
terraform -chdir=live\dev\stack init -reconfigure -backend-config=..\env1\backend.hcl

# 3. Plan with account values + env1 values, save the plan next to env1
terraform -chdir=live\dev\stack plan `
    -var-file=..\account.tfvars `
    -var-file=..\env1\terraform.tfvars `
    -out=..\env1\tfplan

# 4. Apply exactly that plan
terraform -chdir=live\dev\stack apply ..\env1\tfplan

Why each line

LineWhy it is needed
$env:TF_DATA_DIR = "..\env1\.terraform"The most important line. Terraform caches the backend pointer in .terraform/. If env1 and env2 shared stack/.terraform/, a plan for env1 could be applied onto env2's state. A separate data dir per env makes that impossible. Paths are relative to stack/ because -chdir moves there.
init -reconfigureForces Terraform to re-read the backend config instead of trusting the cached one. Harmless when nothing changed, essential when you switch from env1 to env2.
-backend-config=..\env1\backend.hclSets the state key to dev/env1/app/terraform.tfstate. Same bucket as 02-eks, different key.
-var-file=..\account.tfvarsaccount_id, region, state_bucket (used by stack/eks.tf to find the 02-eks state).
-var-file=..\env1\terraform.tfvarsenv_name = "env1" goes into every resource name, plus bucket settings and eks_enabled.
-out=..\env1\tfplan then apply ..\env1\tfplanApply never re-plans. What the reviewer saw is what runs. Also the reason the wrapper refuses to apply without a saved plan.

Step 4 — Join env1 to the shared cluster per env, after step 2

Why a separate step: eks_enabled defaults to false so an env can be created before the cluster exists, and so test/prod envs plan clean until their account's 02-eks is applied. Flipping it adds exactly one thing: an IAM role that only pods in namespace env1, service account app, can assume. env2 gets its own role; neither can use the other's.

1. Edit live/dev/env1/terraform.tfvars

eks_enabled = true     # was false

2. Re-run step 3 (init is already done, but re-running it is harmless)

$env:TF_DATA_DIR = "..\env1\.terraform"
terraform -chdir=live\dev\stack plan  -var-file=..\account.tfvars -var-file=..\env1\terraform.tfvars -out=..\env1\tfplan
terraform -chdir=live\dev\stack apply ..\env1\tfplan

Teardown order

env3 → env2 → env1 → 02-eks → bootstrap

Reverse of creation. An env can be destroyed any time (nothing depends on it). 02-eks can be destroyed only after every env has eks_enabled = false applied, otherwise their IRSA roles point at a deleted OIDC provider.

$env:TF_DATA_DIR = "..\env1\.terraform"
terraform -chdir=live\dev\stack destroy -var-file=..\account.tfvars -var-file=..\env1\terraform.tfvars
